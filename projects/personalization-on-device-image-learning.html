Personalization: On-Device Image Learning

iOS app that learns new image classes from a handful of photos entirely on the phone: a frozen Core ML backbone turns each photo into a vector, a small classifier is fit on the device, and only the vectors are stored.

ARCHITECTURE

PROBLEM

Teaching an app your own objects usually means uploading photos to a server. This app learns new classes from a few photos on the phone itself, with no network code, so nothing leaves the device.

KEY DECISIONS AND TRADE-OFFS

DECISION 1
Freeze a Core ML backbone and fit only a small classifier head on the device
TRADE-OFF
Learning from one or two photos is fast and cheap, but accuracy depends on the backbone: MobileNetV3 at one photo per class is the weakest result (0.834) versus 0.996 for DINOv2-small.
DECISION 2
Store only embedding vectors, not photos, and ship no network code or analytics
TRADE-OFF
Privacy rests on build settings and a source audit, not a formal guarantee, and photos are kept if the user turns off deleting them after embedding.
DECISION 3
Offer two heads: nearest class mean and a logistic head
TRADE-OFF
Nearest class mean never forgets earlier classes because class means don't change; logistic is slightly better for MobileNetV3 at five photos (+0.009) but forgets almost everything without replay.
DECISION 4
Check the Swift classifier against the Python reference with a shared fixture
TRADE-OFF
Probabilities agree within 1e-4, but that only proves the Swift code matches my own Python code, not that either is optimal.

RESULT

Real iPhone vs Python embeddings, MobileNetV3, 20 images

On a 2000-image Flowers102 subset, DINOv2-small reaches 0.996 accuracy with one photo per class (5-way) and rejects unseen classes with AUROC 0.994. On one real iPhone, MobileNetV3 embeddings matched the Python ones with mean cosine 0.9945. Not yet measured: on-device latency, the Pets dataset, photos from real users, and a phone check for the DINO models. The numbers are a preview.
